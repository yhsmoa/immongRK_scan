# 출고스캔 [가상스캔] 설계 — 박스 크기 예상 배정 + 확정 시 스캔 저장

> 작성: 2026-10-08 · 대상: `/shipScan` (shipScan.html, routes/rkShipScan.js)
> 전제 설계: docs/plan-ship-scan.md (박스/아이템 테이블, SET 저장, 확정수량 한도)

## 0. 목표

- [목록]과 [저장] 사이에 **[가상스캔]** 버튼 추가
- 클릭 시 발주서의 **출고 대상 수량(재고+입고 배정분)** 을 박스 크기별 용량에 맞춰 **박스 번호·크기·담을 상품**을 미리 계산해 모달로 보여준다
- 옷 포장이라 눌리는 것을 감안해 **용량의 10% 를 더 담는다** — 모달 상단에 명시
- **이미 있는 박스**(저장분·세션분)는 남은 용량만큼 먼저 채운다
- [확정] → 실제로 그렇게 스캔한 것처럼 박스/아이템을 반영하고 **바로 저장**(기존 `/api/ship-scan/save` SET 경로 그대로)

## 1. 조사 결과 (설계의 근거)

### 1-1. "미리 배정받은 값" = `rk_shipping_list` (출고예정), `prepared_qty` 아님

| 항목 | 값 |
|---|---|
| 진행중 발주서 원본 상품행 | 3,640행 (180개 발주서) |
| `rk_order_items.prepared_qty` (준비) | **전부 NULL** — 마지막 사용 2026-08-31 |
| `rk_shipping_list` status=출고예정 (재고+입고) 배정이 있는 행 | 2,135행 |
| 스캔이 있는 112개 발주서: 스캔량 = 배정량 | **2,569 / 2,829행 (91%)** · 적게 214 · 많게 46 |

→ 가상스캔의 **바코드별 목표 수량 = min(배정량, 확정수량) − 이미 스캔량**. 배정량 = `rk_shipping_list` 의 `status='출고예정'` 행 qty 합(source 재고+입고).
→ 현재 출고스캔 화면의 **준비 열은 사실상 0만 표시**되고 있다(prepared_qty 미사용). 이번에 같은 값(배정량)으로 바꿔 표시한다. (§7 질문 4)

### 1-2. 상품 사이즈 (`coupang_items`, mm·g)

| 항목 | 값 |
|---|---|
| 진행중 발주 상품 2,627종 중 사이즈 보유 | **2,627종 (100%)** — 10/07 상품관리 엑셀 업로드로 채움 |
| 임시값 300×300×20 (1.8 L) | 618종 (23.5%) |
| 측정 상품의 1개당 부피 | 중앙값 **2.85 L**, p90 6.0 L, 최대 45 L |
| 1개당 무게 | 중앙값 200 g, 최대 947 g |

→ 부피 = 가로×세로×높이(mm³ → L). **임시값 상품은 2.85 L 로 가정**하고 모달에 ⚠ 표시.
→ 옷은 접히므로 모서리 길이 제약은 두지 않는다(부피만 본다).

### 1-3. 박스 용량은 "박스 부피 +10%" 로는 안 된다 — 과거 데이터로 보정

과거 출고 박스(`rk_ship_boxes` 1,767개)에 실제 담긴 상품의 **명목 부피 합**(coupang_items 사이즈 기준). 발주서 안에서 **마지막 박스가 아닌 박스 = 꽉 채운 박스**로 보고 집계.

| 크기 | 실제 박스 부피 | 꽉 찬 박스 수 | 명목 부피 합 p20 / **중앙값** / p80 | 상품 수 중앙값 | 무게 중앙값 / p90 / 최대 |
|---|---|---|---|---|---|
| 극소 (봉투 50×60) | — | 207 | 12.5 / **29.1** / 56.2 L | 10개 | 2.1 / 4.9 / 21.6 kg |
| 소 | (미지정) | 4 | 66 / **73** / 80 L | 22개 | 4.7 / 5.3 / 5.3 kg |
| 중 (50×40×30 = 60 L) | 60 L | 156 | 76 / **101** / 142 L | 30개 | 7.0 / 11.3 / 16.5 kg |
| 대 | (미지정) | 3 | 197 / **208** / 233 L | 69개 | 14.3 / 15.2 / 15.4 kg |
| 대2 (50×50×45 = 112.5 L) | 112.5 L | 265 | 171 / **240** / 335 L | 63개 | 17.1 / 21.1 / 35.5 kg |

- 명목 부피 합이 박스 부피의 **약 1.7~2.1배(중앙값), 2.4~3배(p80)** — 옷이 눌려 들어가기 때문. 박스 부피 × 1.1 로 계산하면 실제의 절반도 못 담는다.
- 발주서당 박스 수 중앙값 1개, p90 2개, 최대 11개. 발주서 안 크기 종류 중앙값 1, 최대 3.

**용량 기준값(제안)** — "명목 부피 합" 단위. 10% 가산 전 base 와 가산 후 값:

| 크기 | base | **+10% 적용 용량** | 과거 꽉 찬 박스 대비 | 무게 경고 기준 |
|---|---|---|---|---|
| 극소 | 36 L | **40 L** (≈14개) | 약 p65 | 5 kg |
| 중 | 120 L | **132 L** (≈46개) | 약 p75 | 12 kg |
| 대2 | 280 L | **308 L** (≈108개) | 약 p75 | 20 kg |
| 소 (기존 박스 채우기 전용) | 72 L | 79 L | 표본 4개, 신뢰 낮음 | 6 kg |
| 대 (기존 박스 채우기 전용) | 210 L | 231 L | 표본 3개, 신뢰 낮음 | 16 kg |

- 상수는 `virtualPack.js` 상단 `CONFIG` 한 곳에 두고 모달에 그대로 표시한다. 운영하며 숫자만 조정.
- 대안(기하 방식: 박스 부피 × 압축계수 k)도 가능하지만 중 2.2×, 대2 2.7× 로 계수가 달라 과거 실적 기준이 더 솔직하다.

## 3. 배정 알고리즘 (`virtualPack.js` — 순수 함수, DOM 없음)

```js
planVirtualScan({ products, boxItems, savedBoxes, boxSizeMap }, CONFIG) → plan
```

**입력 정리**
1. 바코드별 `remain = max(0, min(allocQty, confirmedQty) − scannedQty)`. remain=0 → 제외(사유 기록: 배정 없음 / 이미 완료).
2. 1개 부피 `unitL` = w·l·h/1e6. 임시값(300×300×20)·누락 → `CONFIG.defaultUnitL`(2.85) + `flag='assumed'`. 1개 무게 `unitKg` = g/1000 (없으면 0.2).
3. 정렬: **위치 → 바코드** (스캔목록 `shipSorted()` 와 같은 숫자 인식 정렬). 같은 바코드는 연속, 같은 구역 상품이 같은 박스에 모이도록(피킹 동선).

**박스 큐**
4. **기존 박스**(savedBoxes ∪ boxItems 의 boxNo, 오름차순): `cap = CONFIG.cap[size]`, `used = Σ qty·unitL`, `free = cap − used`. `free ≥ 가장 작은 unitL` 이면 채움 대상. 크기 미지정 박스는 '극소' 로 본다(`doScan` 의 기본값과 동일).
5. 남은 총 부피 `V` = 전체 − 기존 박스에 들어갈 양(4를 실제 시뮬레이션해 계산).
6. **신규 박스 크기 결정** (극소/중/대2 만 사용):
   - `n = ceil(V / cap.대2)`; n=0 이면 신규 없음
   - 마지막 박스 부피 `r = V − (n−1)·cap.대2` → `r ≤ cap.극소` 면 극소, `≤ cap.중` 이면 중, 아니면 대2
   - 예: V=600 → 대2 + 대2(292→대2) / V=400 → 대2 + 중(92) / V=320 → 대2 + 극소(12) / V=100 → 중 1개
7. 신규 박스 번호 = 1~20 중 **사용 안 된 가장 작은 번호**부터. 모자라면 계산 중단 + 사유 반환.

**채우기**
8. 큐 순서대로 first-fit: 현재 박스 `free` 에 `floor(free / unitL)` 개까지 담고 나머지는 다음 박스로(바코드 분할 허용 — 실제 스캔과 동일). 
9. 마지막 박스에서 넘치면(이산 단위 때문에 생길 수 있음) **마지막 박스는 용량 초과 허용**하되 채움률 >100% 로 ⚠ 표시; 초과분이 `cap.극소` 를 넘으면 극소/중/대2 중 맞는 크기로 박스 1개 추가.
10. 무게: 박스별 Σ qty·unitKg. `CONFIG.weightWarn[size]` 초과 시 ⚠ (차단 아님 — §7 질문 2).

**출력**
```js
{ ok, reason, assumptions:{overfill:0.10, cap, defaultUnitL, assumedCount},
  boxes:[{boxNo, size, isNew, usedBefore, usedAfter, cap, fillPct, kg, items:[{barcode,name,location,qty,unitL,flag}], warnings:[]}],
  excluded:[{barcode,name,reason}], totals:{skus,qty,L,kg,newBoxes,topUpBoxes}, warnings:[] }
```

## 4. 서버 (routes/rkShipScan.js)

`GET /api/ship-scan/order/:orderNumber` 응답의 `products[]` 에 추가 (조회 1회에 끝내려 신규 엔드포인트 대신 확장):

| 필드 | 출처 | 비고 |
|---|---|---|
| `allocQty` | `rk_shipping_list` status=출고예정, order_number·barcode 별 qty 합(source 재고+입고) | 없으면 0 |
| `size` | `coupang_items` barcode 로 `{w,l,h,g}` (200개씩 in) | 없으면 null |

- 쓰기 엔드포인트는 **추가하지 않는다.** 확정은 기존 `POST /api/ship-scan/save` (SET) 로 가고, 서버의 확정수량 한도·DONE 검증을 그대로 거친다.
- `preparedQty` 는 유지하되 화면 준비 열은 `preparedQty ?? allocQty` 로 표시(§7 질문 4 확정 후).

## 7. 결정 사항 (2026-10-08 확정)

1. **용량 기준값** 극소 40 L · 중 132 L · 대2 308 L (10% 포함, 명목 부피 기준) ✅
2. **무게**: 박스당 **25 kg 미만**. 넘기 전에 다음 박스로 나눈다 (경고가 아니라 제약) ✅
3. 신규 박스는 **극소/중/대2 만** ✅. 기존에 열려 있는 소/대 박스는 용량 기준이 없으므로 채우지 않고 경고만 표시.
4. 계산 기준은 **출고예정 배정량(입고+재고)** ✅. 단 **준비 열은 손대지 않는다** — 기능은 그대로 두고(지금 개선 중이라 안 쓰는 것뿐) 가상스캔 계산에만 배정량을 쓴다.
5. 배치 순서는 **수량 많은 상품부터** ✅ (위치순 아님 — 발주서에서 양 많은 것부터 찾아 담는 게 편함). §3-3 의 정렬 규칙을 이것으로 대체.
7. **기존 박스는 마지막 박스만 채운다** (2026-10-08 추가): 기존 박스가 1·2·3 이면 **3번만** 더 채울 수 있다. 1·2 는 이미 마감(테이핑)된 것으로 보고 건드리지 않는다 — 여유가 남아 있어도 마찬가지. 마지막 박스가 소/대라 용량 기준이 없으면 아무 기존 박스도 채우지 않는다(앞 박스로 거슬러 가지 않음). §3-4 의 "기존 박스 오름차순으로 채움" 규칙을 이것으로 대체.
8. **마지막 박스 크기 UP** (2026-10-08 추가): 마지막 기존 박스가 극소/중인데 남은 상품이 그 용량(부피)에 다 안 들어가면, 다 들어가는 가장 작은 크기(극소→중→대2)로 올린다. 대2 로도 안 들어가면 대2 로 올리고 나머지는 새 박스. 무게 때문에 못 담는 경우는 올리지 않는다(박스를 키워도 해결 안 됨). 카드에 `극소 → 중` 배지와 "크기 UP" 표시, [확정] 시 `saveShip()` 이 바뀐 크기를 보내 서버가 `rk_ship_boxes.box_size` 를 갱신한다. `CONFIG.upgradeLastBox` (기본 true).

    이미 스캔한 개수는 입고분부터 뺀다. 모달 상단 [입고·재고 나눠 담기]/[같이 담기] (localStorage `shipScan.vsSplit`, 기본 분리),

13. **입고정리 [가상스캔] 일괄** (2026-10-15 추가): 입고정리(/inboundArrange)의 [출고준비]와 [박스라벨출력] 사이에 [가상스캔] 버튼.

    옵션은 모달 상단에서 **기존 박스(채우기/새 박스만, 매번 직접 고름)** · **대상(전체/입고/재고, 이 화면만 '입고' 기본 선택)** ·
    **입고코드 = 드롭박스에서 고른 코드로 고정**. 옵션을 다 고르면 서버 `POST /api/ship-scan/virtual-batch` (confirm:false, 읽기만)로
    발주서별 한 줄 요약(상태 · 대상 개수/종수 · 예상 박스 칩 · 제외 사유 · 경고)을 표로 보여 주고, 발주서 단위로 빼고 [확정](confirm:true).
    확정은 서버가 발주서마다 **그 시점 DB 로 계획을 다시 계산**해 `applyPlan` → `saveShipState` 로 저장한다(확정수량 한도·처리완료 검증 그대로).

    체크 상태는 유지해 바로 [박스라벨출력]으로 이어간다. 운영 전제: 출고스캔 페이지에 발주서를 열어 둔 채로 일괄을 돌리지 않는다
    (출고스캔 [저장]은 화면 상태 SET 이라 나중에 저장하는 쪽이 이긴다).

14. **용량 = 실제 박스 표본의 최댓값** (2026-10-15): "중 박스에 16개밖에 안 들어간다" 는 현장 지적으로 점검.

    오류 가능), 백분위 같은 통계값도 쓰지 않는다(덜 찬 마지막 박스가 섞여 낮게 나온다). 수량이 그 크기의 상위 5% 를 넘는 박스는 크기 기록 의심으로 뺀다
    (저장 시 크기를 안 고르면 '극소' 로 들어가는 기본값 때문에 극소에 60개짜리 박스가 있다).

    테스트는 고정 보정값(TEST_CAL: 36/120/280 · 5% · 25 kg)으로 알고리즘을 보고, 기본값은 별도 테스트로 본다.
    다시 잡으려면 (Supabase SQL) 박스별 명목 부피 합 = Σ qty × (coupang_items 가로×세로×높이 mm / 1e6, 임시값 300×300×20·누락은 2.85 L) 를 크기별로 내림차순.

15. **이미 담긴 분량의 출처 귀속** (2026-10-15 수정): §7-10 의 "이미 스캔한 개수는 입고분부터 뺀다" 는 가상스캔 분량에만 맞는 규칙이었다.
