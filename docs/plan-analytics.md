# 데이터 분석 (/analytics) — 발주수량 · 확정수량 추이

> 2026-10-21 · 홈 REFERENCE 카드와 상단 메뉴의 **라벨 설정** 바로 옆에 **데이터 분석**
> 파일: `analytics.html` · `routes/rkAnalytics.js` · `supabase/rk_order_stats.sql` (DB 적용 완료)
> 2026-11-12 과거 발주 이력(2022-07 ~ 2026-07) 추가 — §6 · `supabase/rk_order_history.sql` · `scripts/load-order-history.js`

## 1. 페이지의 의도

쿠팡이 넣는 발주가 **언제 · 얼마나** 들어오고, 그중 **얼마를 확정(납품)** 하는지를 일 · 주 · 월 · 연도로 본다.
보려는 질문:

| 질문 | 어디서 보나 |
|---|---|
| 이번 주/달 발주가 늘었나 줄었나 | 지표 타일(전 기간 대비) · 추이 차트 |
| 발주 중 얼마를 납품하고 있나 (확정률) | 확정률 타일 · 확정률 선 차트 · 표 |
| 못 맞춘 수량(미확정)은 얼마이고 어느 상품인가 | 미확정 타일 · 상품별 [미확정 많은 순] |
| 발주는 무슨 요일에 들어오나 (작업 계획) | 요일별 발주 |
| 어느 센터 · 브랜드 비중이 큰가 | 물류센터별 · 브랜드별 (행 클릭 = 필터) |
| 작년 같은 달과 비교하면 | 연도별 · 월별 비교 (해가 바뀌면 전년 대비 열이 생긴다) |
| 입고 일정 기준으로는 | 날짜 기준 [입고예정일] |

## 2. 꼭 알아야 할 데이터 사실 (2026-10-21 확인)

- **`rk_order_items.confirmed_qty` 는 쓸 수 없다.** 업로드 시점(발주상태 "거래처확인요청") 값이라 34,257행 모두 발주수량과 같다.
- **진짜 확정수량 = 출고스캔(`rk_ship_box_items`) 발주번호+바코드별 qty 합.** 쿠팡에 올리는 "발주리스트 확정" 파일(`/api/orders/export`)의 확정수량과 같은 규칙.
- 진행중(PROCESSING) 발주서는 스캔이 아직 늘어난다 → 확정률 · 미확정은 **처리완료(DONE) 발주서만**으로 계산하고, 진행중 확정분은 차트에서 빗금으로 따로 그린다.
- DONE 인데 스캔 0 인 발주서(월 13~100건)는 전량 미납 = 확정 0 으로 센다.
- 한 발주서의 품목은 모두 같은 발주등록일이다 (날짜별 발주서 수를 더해도 겹치지 않음).
- 쿠팡 발주는 **월 · 수에 몰린다** (발주수량의 86%).
- 운영 DB(`rk_orders`)는 발주일 2026-07-16 · 입고예정일 2026-07-27 부터 (MongoDB 이전 자료는 없음). 그 앞은 과거 발주 이력(§6)이 채운다. 매입가는 부가세 포함 단가.

## 3. 화면 구성

1. **필터 한 줄** (아래 전부에 적용): 기간 프리셋(최근 4주 · 이번 달 · 최근 90일 · 올해 · 전체 · 직접) + 연도 선택, 날짜 기준(발주일 · 입고예정일), 브랜드, 센터, [새로고침]
2. **지표 6개**: 발주수량 · 확정수량(진행중 별도) · 확정률 · 미확정 수량 · 발주서(SKU · 진행중) · 발주금액(확정금액). 앞의 같은 길이 기간과 비교 — 앞 기간이 자료 시작일 이전에 걸치면 비교하지 않는다
3. **추이**: [일별 · 주별 · 월별] 막대(발주 파랑 · 확정 주황 · 진행중 빗금) + 아래에 확정률 선(별도 차트 — 축 두 개를 겹치지 않는다). 발주 없는 날·주도 0 으로 채워 간격을 맞추고, 고른 기간에 일부만 걸친 주·월은 `*`
4. **기간별 상세 표** (최근이 위) + CSV 내려받기
5. **연도 × 월 표** (기간과 무관하게 전체 · 해가 둘 이상이면 전년 대비)
6. **요일별** 하루 평균 발주수량 · **브랜드별** · **물류센터별** · **상품별**(발주 많은 순 / 미확정 많은 순, 상위 30)
7. **계산 기준** 설명

색: 발주 `#2a78d6` · 확정 `#eb6834` — dataviz 검증 스크립트 통과(색각 이상 ΔE 24.7, 대비 3:1 이상).

## 4. API · DB

- `GET /api/analytics?from&to&basis=reg|arrival&brand&center&fresh=1` → `rk_order_stats` jsonb 그대로 + `filters` · `generatedAt` · `cached`
- 서버 메모리에 **같은 조건 5분** 캐시 (최대 60개). [새로고침] = `fresh=1`
- `rk_order_stats(p_from, p_to, p_basis, p_brand, p_center)` → `{ range, totals, prev, series:{day,week,month}, weekday, centers, brands, products, years, meta, centerList }`
  - 실행 권한은 `service_role` 만 (매출 집계라 anon 키로 못 부르게)
  - 기간 10년(3700일) 이내 (2026-11-12 3년 → 10년)
  - `meta.histMax` = 과거 발주 이력의 마지막 날짜(날짜 기준에 따라 발주일/입고예정일) — 화면 "계산 기준" 의 [과거 발주] 줄

### 성능 메모

- 지금(품목 3.4만 행) **약 1.7초**. 연도 × 월 표가 전체 기간을 보므로 기간을 줄여도 거의 같다.
- 빨라진 것: 발주서 단위로 먼저 묶어 `count(distinct order_id)` 제거, 문자열 키 `collate "C"` (기본 ICU 정렬로 count(distinct) 하면 5배 느림), 상품명 정규식은 바코드마다 한 번, `work_mem 64MB`.
- 효과 없던 것: 출고스캔 합을 발주번호로 좁히기(오히려 느림), 동적 SQL(EXECUTE).
- 과거 발주 이력(19만 줄)은 §6 방식(요약 테이블 + 기간 색인)이라 이 숫자에 넣지 않는다.
- **운영 품목이 15만 행을 넘어 5초 이상 걸리면**: 발주서 × 바코드 단위 일별 요약 테이블(또는 materialized view)을 두고 업로드 · 처리완료 · 스캔 저장 때 갱신하거나 밤마다 새로 고치는 방식으로 바꾼다.

## 6. 과거 발주 이력 (2026-11-12)

운영 DB 이전의 발주를 2022년부터 이어서 보려고, 쿠팡 서플라이어 허브의 **발주 SKU 목록** 엑셀을 별도 테이블에 넣었다.

| | |
|---|---|
| 원본 | `쿠팡_발주SKU_입고예정_2022-07-27_2026-07-26.xlsx` — 발주서 10,167건 · SKU 줄 194,133행 · 바코드 13,958종 |
| 범위 | 입고예정일 2022-07-27 ~ 2026-07-24 · 발주일 2022-07-16 ~ 2026-07-21 (운영 DB 와 발주번호 겹침 0) |
| 합계 | 발주 738,569 · 확정 408,360 · 입고 400,469 · 발주금액 8,701,707,882원 |
| 테이블 | `rk_order_history` (발주번호 × 바코드, 원본) · `rk_order_history_ord` (발주번호 × 브랜드 요약, 14,422행) |
| 적재 | `node scripts/load-order-history.js <엑셀> [--dry]` — 검증 → upsert → 요약 재생성 → DB 를 다시 읽어 한 줄씩 대조 |

**운영 테이블에 넣지 않은 이유**: 발주서 목록 · 출고스캔 · 랭킹 화면에 1만 건이 섞이면 안 되고, 과거 자료는 출고스캔 기록이 없어 확정수량의 출처가 다르다.

**집계 규칙** (운영 자료와 한 함수 `rk_order_stats` 에서 합친다)
- 확정수량 = 파일의 **확정수량** 열(쿠팡에 확정해 올린 값). 과거 발주서는 모두 처리완료로 센다 → 확정률 · 미확정에 그대로 들어간다.
- 발주일 = 파일의 발주일(한국 시각)의 날짜, 브랜드 = 상품명 앞머리(운영과 같은 규칙, 테이블의 생성 열). 금액 = 수량 × 매입가(VAT 포함) — 파일의 금액 열과 전 행 일치.
- 브랜드 "기타" 2,247줄(1.2%): 브랜드명 없이 등록된 2022~2024 초기 상품과 오타("아아이엠몽" · "아이엠모" · "유아몽"). 원본 그대로 두었다.
- 상품명 앞뒤 공백 27건은 떼고 넣었다. 파일의 입고수량(쿠팡이 실제로 받은 수량)도 `received_qty` 로 보관한다 (화면에는 아직 안 쓴다).
- 운영 테이블에 있는 발주번호는 과거 쪽에서 빼고 센다(적재 스크립트도 겹치면 멈춘다).

**속도** — 과거 19만 줄을 매번 읽지 않게 했다
- 발주서 단위 숫자(총계 · 추이 · 요일 · 센터 · 연도표)는 요약 테이블 1.4만 행에서 읽는다.
- 줄 단위(SKU 수 · 브랜드 · 상품)는 **고른 기간의 줄만** 날짜 색인으로 읽는다 → 최근 기간 조회는 과거 자료를 건드리지 않는다.
- `count(distinct)`(묶음마다 정렬) 대신 (날짜, 바코드) 를 해시로 한 번 줄여 센다. 기간 안의 줄(cur)은 상품명 · 센터를 빼 좁게 둔다.
- `plan_cache_mode = force_custom_plan` — 받은 기간으로 계획을 세워 색인을 고른다. (브랜드 필터 조회가 2.5초 → 0.6초로 줄어든 것도 이 영향)
- 로컬 Postgres(PGlite, 운영과 비슷한 속도)에서: 최근 4주 0.5초 · 최근 90일 0.65초(전과 같음) · 1년 1.0초 · 전체 4년 2.2초. 같은 조건은 서버가 5분 담아 둔다.

**검증** (2026-11-12, 로컬 Postgres 에 운영 스냅샷 + 엑셀을 올려서)
- 운영만 있는 기간: 새 함수 = 예전 함수 (전 구획 동일). 로컬 모의 = 운영 DB 응답 (전 구획 동일).
- 과거 포함 14개 조건(전체 · 1년 · 경계 · 브랜드 · 센터 · 빈 기간): 독립 JS 구현과 총계 · 전 기간 · 일/주/월 · 요일 · 센터 · 브랜드 · 상품 · 연도표 일치.
- 겹친 발주번호 · 센터가 어긋난 발주서 · (발주번호, 바코드) 중복은 거부/제외되는지 확인.

**다른 기간 파일을 더 넣을 때**: 같은 스크립트로 넣으면 이어 붙는다(유일키 upsert). 운영 DB 와 겹치는 발주서는 엑셀에서 빼야 한다.
