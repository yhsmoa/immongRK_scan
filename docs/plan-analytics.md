# 데이터 분석 (/analytics) — 발주수량 · 확정수량 추이

> 2026-10-21 · 홈 REFERENCE 카드와 상단 메뉴의 **라벨 설정** 바로 옆에 **데이터 분석**
> 파일: `analytics.html` · `routes/rkAnalytics.js` · `supabase/rk_order_stats.sql` (DB 적용 완료)

## 1. 페이지의 의도

쿠팡이 넣는 발주가 **언제 · 얼마나** 들어오고, 그중 **얼마를 확정(납품)** 하는지를 일 · 주 · 월 · 연도로 본다.
보려는 질문:

| 질문 | 어디서 보나 |
|---|---|
| 이번 주/달 발주가 늘었나 줄었나 | 지표 타일(전 기간 대비) · 추이 차트 |
| 발주 중 얼마를 납품하고 있나 (확정률) | 확정률 타일 · 확정률 선 차트 · 표 |
| 못 맞춘 수량(미확정)은 얼마이고 어느 상품인가 | 미확정 타일 · 상품별 [미확정 많은 순] |
| 발주는 무슨 요일에 들어오나 (작업 계획) | 요일별 발주 |
| 어느 센터 · 브랜드 비중이 큰가 | 물류센터별 · 브랜드별 (행 클릭 = 필터) |
| 작년 같은 달과 비교하면 | 연도별 · 월별 비교 (해가 바뀌면 전년 대비 열이 생긴다) |
| 입고 일정 기준으로는 | 날짜 기준 [입고예정일] |

## 2. 꼭 알아야 할 데이터 사실 (2026-10-21 확인)

- **`rk_order_items.confirmed_qty` 는 쓸 수 없다.** 업로드 시점(발주상태 "거래처확인요청") 값이라 34,257행 모두 발주수량과 같다.
- **진짜 확정수량 = 출고스캔(`rk_ship_box_items`) 발주번호+바코드별 qty 합.** 쿠팡에 올리는 "발주리스트 확정" 파일(`/api/orders/export`)의 확정수량과 같은 규칙.
- 진행중(PROCESSING) 발주서는 스캔이 아직 늘어난다 → 확정률 · 미확정은 **처리완료(DONE) 발주서만**으로 계산하고, 진행중 확정분은 차트에서 빗금으로 따로 그린다.
- DONE 인데 스캔 0 인 발주서(월 13~100건)는 전량 미납 = 확정 0 으로 센다.
- 한 발주서의 품목은 모두 같은 발주등록일이다 (날짜별 발주서 수를 더해도 겹치지 않음).
- 쿠팡 발주는 **월 · 수에 몰린다** (발주수량의 86%).
- 데이터 시작 2026-07-16 (MongoDB 이전 자료는 없음). 매입가는 부가세 포함 단가.

## 3. 화면 구성

1. **필터 한 줄** (아래 전부에 적용): 기간 프리셋(최근 4주 · 이번 달 · 최근 90일 · 올해 · 전체 · 직접) + 연도 선택, 날짜 기준(발주일 · 입고예정일), 브랜드, 센터, [새로고침]
2. **지표 6개**: 발주수량 · 확정수량(진행중 별도) · 확정률 · 미확정 수량 · 발주서(SKU · 진행중) · 발주금액(확정금액). 앞의 같은 길이 기간과 비교 — 앞 기간이 자료 시작일 이전에 걸치면 비교하지 않는다
3. **추이**: [일별 · 주별 · 월별] 막대(발주 파랑 · 확정 주황 · 진행중 빗금) + 아래에 확정률 선(별도 차트 — 축 두 개를 겹치지 않는다). 발주 없는 날·주도 0 으로 채워 간격을 맞추고, 고른 기간에 일부만 걸친 주·월은 `*`
4. **기간별 상세 표** (최근이 위) + CSV 내려받기
5. **연도 × 월 표** (기간과 무관하게 전체 · 해가 둘 이상이면 전년 대비)
6. **요일별** 하루 평균 발주수량 · **브랜드별** · **물류센터별** · **상품별**(발주 많은 순 / 미확정 많은 순, 상위 30)
7. **계산 기준** 설명

색: 발주 `#2a78d6` · 확정 `#eb6834` — dataviz 검증 스크립트 통과(색각 이상 ΔE 24.7, 대비 3:1 이상).

## 4. API · DB

- `GET /api/analytics?from&to&basis=reg|arrival&brand&center&fresh=1` → `rk_order_stats` jsonb 그대로 + `filters` · `generatedAt` · `cached`
- 서버 메모리에 **같은 조건 5분** 캐시 (최대 60개). [새로고침] = `fresh=1`
- `rk_order_stats(p_from, p_to, p_basis, p_brand, p_center)` → `{ range, totals, prev, series:{day,week,month}, weekday, centers, brands, products, years, meta, centerList }`
  - 실행 권한은 `service_role` 만 (매출 집계라 anon 키로 못 부르게)
  - 기간 3년 이내

### 성능 메모

- 지금(품목 3.4만 행) **약 1.7초**. 연도 × 월 표가 전체 기간을 보므로 기간을 줄여도 거의 같다.
- 빨라진 것: 발주서 단위로 먼저 묶어 `count(distinct order_id)` 제거, 문자열 키 `collate "C"` (기본 ICU 정렬로 count(distinct) 하면 5배 느림), 상품명 정규식은 바코드마다 한 번, `work_mem 64MB`.
- 효과 없던 것: 출고스캔 합을 발주번호로 좁히기(오히려 느림), 동적 SQL(EXECUTE).
- **품목이 15만 행을 넘어 5초 이상 걸리면**: 발주서 × 바코드 단위 일별 요약 테이블(또는 materialized view)을 두고 업로드 · 처리완료 · 스캔 저장 때 갱신하거나 밤마다 새로 고치는 방식으로 바꾼다.

## 5. 남은 후보

- 입고예정일 기준일 때 프리셋 끝을 오늘이 아니라 앞으로의 입고예정일까지 늘리기 (지금은 [연도] 나 [직접]으로 본다)
- 미납 사유(`shortage_reason`) 분석 — 지금은 45건뿐이라 뺐다
- 상품 행 클릭 → 그 상품의 주별 추이
